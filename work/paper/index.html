Predicting Content Decay in Organic Search:
A Baseline ML Approach on Real Production Data

Author Saif Ullah Arshad Role ML Engineering Intern, FlyRank AI Institution Information Technology University, Lahore Date August 2026 Dataset FlyRank ML Internship Dataset (30K sample · 79M row warehouse) Code github.com/Saif-Ullah0/flyrank-ml-internship

Abstract

This paper examines whether a machine learning classifier can identify web pages at risk of organic search traffic decay more reliably than a hand-written rule. Using a 30,000-row anonymised sample of real client search data provided by FlyRank AI, we framed the problem as binary classification (declining vs. not declining), trained a Random Forest with a client-holdout split to prevent data leakage, and compared results against a staleness-and-visibility baseline rule. The baseline rule achieved Precision@50 of 0.640; the trained Random Forest matched this score on the held-out sample. A key finding was that six features originally included in the feature set encoded the month-over-month comparison used to construct the label, inflating validation scores to 1.000 before removal. After correcting for leakage, results were honest but modest: the 30,000-row sample appears insufficient to separate a tuned model from a well-designed rule. Validation on the full 79M-row warehouse dataset is the recommended next step before drawing stronger conclusions.

Introduction / Problem Statement

Organic search traffic is a compounding asset: content that ranks well continues to generate visitors without ongoing spend. However, pages lose rankings over time as competitors publish fresher content, search algorithms update, and AI-generated summaries reduce click-through rates on lower-ranked results.

FlyRank's content teams manage large portfolios of client pages. Deciding which pages to refresh first is a resource allocation problem. The current approach uses a hand-written rule: flag pages that are stale (not updated recently) and visible (receiving impressions). This rule achieved Precision@50 of 0.240 on an initial evaluation using a different feature set (Notebook 01, starter pipeline), suggesting that the majority of pages it flags are not actually declining.

The research question is: can a machine learning model, trained on observable search signals, outperform a hand-written rule at identifying pages that will experience traffic decay?

A secondary question emerged during the work: how much does the choice of validation split affect the apparent performance of such a model? The answer, documented in the validation audit (Week 6), was substantial.

Label Definition

The target variable is_declining_label is derived from trend_direction == "down". This is a proxy label: it captures observed trailing trend, not a directly measured future outcome. A page labelled declining may have already recovered by the time it is reviewed.

Declining rate in the sample: 54.2% of pages are labelled as declining.

Excluded Features and Why

Six features were excluded after being identified as temporally leaky. Each encodes the month-over-month comparison that generates the trend_direction label:

Excluded: trend_direction    (IS the label source)
Excluded: trend_pct           (derived from label)
Excluded: impressions_last_30d  (encodes recent month)
Excluded: impressions_prev_30d  (encodes previous month)
Excluded: clicks_last_30d       (same temporal issue)
Excluded: clicks_prev_30d       (same temporal issue)

Including any of these features produced Precision@50 of 1.000 during training — a leakage signal, not a model quality signal.

Validation Design

A client-holdout grouped split was used. All pages from a given client appear in either the training set or the test set, never both. This prevents the model from learning client-specific patterns and reporting inflated generalisation performance.

Test size: 20% of clients (7 of 32), yielding 6,163 test pages and 23,837 training pages.

Baseline

The Week 4 hand-written rule scores pages on a weighted combination of normalised staleness and log-scaled visibility:

baseline_score = 0.6 × norm(days_since_last_update)
              + 0.4 × log_norm(impressions_90d)

This rule achieved Precision@50 of 0.640 on the full sample.

Models Trained

Four models were trained and compared against the baseline on the same client-holdout split and the same Precision@50 metric:

  • Logistic Regression (linear baseline)
  • Decision Tree (depth 5, interpretable)
  • Random Forest (100 trees, depth 10, primary model)
  • Gradient Boosting (100 estimators, depth 4)

All models used class_weight='balanced' to account for the 54.2% declining rate.

The Split Inflation Finding

A key result from the validation audit: using a naive random split instead of the client-holdout split inflated the Random Forest score from 0.640 to 0.920 — a difference of +0.280. This optimism is entirely an artefact of the validation design, not model quality.

Error Analysis

At Precision@50 = 0.640, approximately 18 of the top 50 flagged pages are false positives (pages the model flags as declining that are not). False positive profile: pages with moderate impressions (~1,746 mean), short staleness (~94 days mean), near-zero CTR, and poor average position (~24). These appear to be pages that rank poorly for reasons unrelated to content decay — competitive displacement or topic relevance loss — rather than content staleness.

Limitations and Honest Framing

LimitationImpact
Trained on 30K sample, not 79M row warehouseResults are directional only. The sample may lack sufficient label variety to differentiate a tuned model from a good rule.
Proxy label from 90-day trailing trendA page may have already recovered by review time. The label captures past trajectory, not future state.
No competitive contextThe model cannot see competitor activity, algorithm updates, or seasonal patterns that explain decline.
Precision@50 = 0.640 means 36% false positivesHuman review is required before any content action. This is a prioritisation tool, not a classifier.
No temporal splitThe client-holdout split is honest but not time-aware. A time-based split would be more realistic for production use.
Prototype, not production systemHas not been stress-tested on new client segments or adversarial inputs.

All claims in this paper use careful language: observed, measured, directional, decision-support. No claim goes beyond what the evidence supports on the 30,000-row sample.

Must Not Be Automated

  • Publishing or editing content based on model score alone
  • Emailing clients about flagged pages without human review
  • Deleting or redirecting pages based on model output
  • Using this output as the sole basis for client reporting
  • Running on client data without explicit consent to ML analysis

Monitoring and Retrain Triggers

Check Precision@50 monthly on fresh data. If it drops below 0.55 consistently, investigate before using the queue. Retrain when: a major algorithm update occurs, a new client segment is added not in training data, or the full 79M row dataset becomes available for training. The last trigger is the most important one.
